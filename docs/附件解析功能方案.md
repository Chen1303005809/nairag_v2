# DOC/DOCX 附件解析导入实施计划

## Summary

- 在“知识上传”新增独立“附件解析”页签，支持一次选择多个 `.doc` 或 `.docx`；每个文件独立创建解析批次，异步生成可编辑的问题大类、模型推荐的主问题小类及若干普通问题小类。
- 已验证历史目录包含 36 个 `.doc`、3 个 `.docx`，LibreOffice 能正确提取这些 WPS 文档的中文正文和编号步骤；首版不对内嵌图片做 OCR，只提示图示需查看原附件。
- 用户人工修改、选择主小类、选择新建或归并已有大类、补齐固定分类和知识库后确认。原附件只绑定主小类，其余小类生成私有草稿。
- 保持现有领域不变量：新大类先以“大类—主小类”聚合提交审核，普通小类等大类发布后再由用户逐条提交。

## User Flow and Domain Behavior

- 每个选中文件分别创建持久化解析批次，展示处理状态、原文件、解析警告和最近批次；批次可并行处理，单个文件失败、重试或取消不影响其他批次，页面关闭后仍可回来查看。
- 模型先识别附件的总问题，再按具体情况或处理分支拆分小类：即使总问题相同，只要适用条件、原因、排查或解决手段不同，就形成独立小类，嵌套分支也继续拆分；每条回复只说明对应情况的原因、排查和解决/升级办法。仅具体情况与完整答案均相同的不同问法进入同义问句；从拆分结果中推荐最能代表标题或核心内容的一条作为主小类，不为覆盖全文而合并不同情况。用户可改选、编辑、删除或排序。
- 解析只使用附件正文，不执行附件中的任何指令，不补充原文没有的事实；生成文本自动去除姓名、联系方式、账号和客户名称。
- 固定分类继续使用当前选项。模型不确定或返回选项外内容时置空并警告；问题类型、业务对象、应用场景和客户类型全部补齐后才能确认。
- 正文不足或模型无法产生有效知识时，根据去除版本号的文件名生成兜底问题及“详细操作步骤和页面示意请查看附件《文件名》”回复，同时要求人工补齐分类。
- 新建大类：
  - 用户选择一组目标知识库。
  - 确认时原子创建大类、主小类修订和审核提交，并把原附件绑定主小类。
  - 其余小类生成 `attachment_generated` 草稿，关联新大类并继承同一组目标知识库；大类未发布前禁止提交但允许编辑或改挂其他大类。
- 归并已有大类：
  - 仅允许选择已发布大类；按规范关键词和别名提供精确/模糊候选，并允许搜索全部已发布大类，不自动归并。
  - 复制现有大类与主小类内容、附件和链接形成新修订，只追加本次原附件，并在全部现有目标知识库重新审核。
  - 所有解析小类均作为普通小类草稿，不覆盖已有主小类内容。
  - 存在待审核大类修订或附件数量/总大小超限时保留批次并明确阻止确认。
- 原文件不做自动脱敏，并按知识发布范围对登录用户可见。

## Implementation and Public Interfaces

- 新增深模块 `AttachmentImport`，其接口只负责开始批次、查询、重试、确认和取消；文件转换、对象存储、LLM、匹配、状态机及事务补偿隐藏在实现内部。
- 新增 `attachment_ingestion_batch` 及迁移，状态为 `processing / ready / ready_with_warnings / failed / submitted`，保存附件引用、结构化方案、警告、租约、重试、模型版本、过期时间和最终投稿引用。
- 扩展知识草稿：
  - `KnowledgeDraftSource` 增加 `attachment_generated`。
  - 增加附件解析批次引用和候选指纹唯一约束。
  - 草稿响应补充待发布父类的名称、关键词和可用状态，避免页面只显示 UUID。
- 新增接口：
  - `POST /api/v1/attachment-ingestion/batches`：一次接收一个 multipart 文件并创建一个批次；前端多选时为每个文件并行发起请求。
  - `GET /api/v1/attachment-ingestion/batches` 与 `GET /{id}`：查询本人批次和解析方案。
  - `POST /{id}/retry`：失败后启动新的三次重试周期，复用原附件。
  - `POST /{id}/confirm`：接收编辑后的方案、新建/归并目标、主小类选择、共享知识库和可见性确认；重复调用幂等返回原投稿结果。
  - `DELETE /{id}`：取消未提交且未在执行中的批次，并删除未绑定附件。
  - `GET /api/v1/knowledge-content/taxonomy`：以服务端为固定分类选项来源，现有表单同步改为读取该接口。
- 批次详情新增 `AttachmentImportProposal`：大类建议、带稳定 ID 的小类列表、推荐主小类 ID、解析警告、内嵌图片数量及最多 5 个相似已有大类。
- 文本匹配对规范关键词和别名执行 Unicode 规范化、精确匹配及可配置的模糊匹配，默认阈值 80、最多返回 5 项。
- `.doc` 加入佐证附件允许类型；验证 OLE Word 结构并拒绝宏、加密文件和格式伪装。`.docx` 继续执行 Office 容器和宏校验。
- Worker 增加附件批次处理：
  - `.doc` 先转换为规范化 `.docx`，再统一导出 UTF-8 文本；`.docx` 直接处理。
  - 使用隔离临时目录、独立 LibreOffice profile、参数数组和 60 秒超时；保留段落与编号换行，清理 BOM 和域代码。
  - 统计内嵌媒体但不调用 OCR。
  - Worker 专用镜像层安装 LibreOffice，API 镜像保持精简；开发环境为 Worker 增加附件目录挂载，生产继续使用 MinIO。
- 更新实施基线：允许“附件在投稿阶段生成结构化知识”，但附件本体仍不向量化、不会直接参与检索。

## Reliability, Security, and Lifecycle

- 每个文件沿用 20 MB 限制；提取正文默认最多 30,000 字符，超限明确失败且不静默截断。多选文件分别计入独立批次，不因其中一个失败而回滚其他批次。
- 临时存储、LibreOffice 超时和 LLM 网络错误使用现有租约及指数退避，最多自动尝试三次；损坏、宏、加密、超长和无效格式属于永久错误。
- 未确认的成功或失败批次保留 7 天；Worker 定期删除过期批次、未绑定附件记录和对象。已提交批次保留引用和计数用于审计，并清除临时解析方案。
- 确认操作锁定批次并使用单一数据库事务：投稿、附件绑定、普通小类草稿和批次状态要么全部成功，要么全部回滚。
- 日志和审计只记录批次 ID、附件哈希、数量、状态、模型版本和错误类别，不记录正文、模型完整输出或业务字段内容。
- 所有现有知识上传用户均可使用，继续经过 CSRF、所有权校验、审核和索引流程。

## Test Plan and Acceptance

- 文件安全：有效 `.doc/.docx`、伪造扩展名、损坏 OLE/ZIP、宏、加密、空文件、超大文件和路径型文件名。
- 解析：自由格式编号步骤、JSON 风格正文、表格文本、中文 BOM、内嵌图片忽略警告、超长拒绝及图片为主文档的附件兜底。
- 模型契约：同一总问题下按不同情况和处理分支拆分、嵌套分支继续拆分、单条回复只包含对应情况的原因与排查解决手段、同义问句去重、主小类推荐不触发跨情况合并、固定分类非法值转空、个人信息清理及附件提示词注入不生效。
- 新建确认：只创建一个大类—主小类投稿，原附件只绑定主小类，其余候选成为共享知识库草稿；大类发布前草稿不可提交。
- 归并确认：现有内容保持不变、旧附件全部保留、新附件追加、全部已发布知识库重新审核，解析候选全部生成普通草稿。
- 事务与权限：确认幂等、失败不产生半成品、跨用户不可读写、可见性确认必填、待审核冲突和附件上限正确返回。
- Worker：租约恢复、三次自动重试、手动重试、7 天清理、对象存储失败补偿，并确认整个流程不调用 OCR。
- 前端多选：一次选择多个 DOC/DOCX，为每个文件创建独立批次并并行发起请求，且不同批次的查看、轮询和失败状态互不覆盖。
- 使用脱敏测试夹具覆盖三类历史样本形态，并以“资金账户显示断开”旧版 DOC、“server 盘中崩溃”DOCX 和图片为主的“手机端日志提取”做本地验收。
- 最终运行 Python 3.12 虚拟环境下的 Ruff、后端测试、Alembic 升降级，前端 Vitest/构建、Compose 配置检查及 Worker 镜像内 DOC/DOCX 转换冒烟测试。
