## 1. 目标与 V1 范围

构建一个单组织、私有化部署的 RAG 知识库系统，包含账号管理、知识库管理、结构化知识投稿、普通子条目草稿、会话智能上传、分库审核、异步嵌入、文本/图片问题检索、会话快速检索、佐证附件展示、有用反馈、结果级不可修改检索 Review 和系统管理员数据面板。最终交付以 `docker-compose.yaml` 编排多容器服务。

V1 明确不包含：

- 多组织或租户隔离，不设置 `organization_id`。
- Excel/CSV 批量导入。
- 基于附件内容的知识检索或附件向量化。
- LLM 生成、改写或总结最终检索答案；LLM 仅可用于已确认的会话知识提取与查询提炼。
- Redis、RabbitMQ 等额外队列基础设施。
- 新建父类—主子条目草稿、已有知识修订草稿、审核前撤回及多候选并行审核。
- 对容量、吞吐或响应时间作性能承诺；当前只以最多约 20 个活跃知识库为规划假设。
- 根据标注自动调整线上分数、阈值或排序；首版只记录和分析。
- 导出 CSV、趋势图、回填历史检索，或保存未展示的隐藏候选。

## 2. 不可破坏的领域不变量

1. 父类是全局问题大类，与知识库和 Milvus Collection 解耦。
2. 每个父类必须且只能有一个主子条目；父类与主子条目原子创建。
3. 主子条目不能删除、不能迁移到其他父类，但可以通过新修订修改。
4. 普通子条目只能在父类已经存在并完成可用审核后创建；不能选择待审核父类。
5. 子条目是业务知识单元，向量分片只是它某一修订的派生检索数据；一个子条目修订可以生成多个向量分片。
6. 知识库与业务上的 Milvus Collection 一一对应；底层允许用多代物理 Collection 完成无中断模型升级。
7. 只有子条目需要按知识库发布。发布状态及当前修订属于 `子条目 × 知识库` 关系，不属于父类。
8. 同一子条目可以投放到多个知识库，各知识库独立审核普通子条目，并可生效不同修订。
9. 普通子条目的目标知识库必须是其父类主子条目已经发布的知识库子集。
10. 父类—主子条目聚合的内容必须保持全局一致，不允许不同知识库展示不同父类版本。
11. PostgreSQL 是发布状态与当前修订的唯一事实来源；Milvus 只是可重建的候选检索索引。
12. 所有已发布内容采用不可变修订；新修订未成功发布前，旧修订继续提供服务。
13. 正常业务流程不物理删除知识历史；使用归档并异步清理对应向量。

## 3. 角色与权限

系统只有三个角色：

| 角色 | 能力 |
| --- | --- |
| 普通用户 | 查询全部知识库；向任意一个或多个知识库投稿 |
| 审查管理员 | 继承普通用户能力；审核分配给自己的知识库中的投稿 |
| 系统管理员 | 管理账号、启停账号、重置凭据、管理知识库、分配角色及“审查管理员 × 知识库”关系；查看数据面板 |

补充规则：

- 不要求提交人与审核人分离，审查管理员可以审核自己提交到其获授权知识库的内容。
- 只有新增普通子条目支持创建者私有草稿；草稿不是候选修订，只有正式提交后才创建不可变候选修订并进入审核。
- 已提交审核的修订锁定，不能修改或由投稿人撤回，只能等待获授权管理员通过或驳回。
- 被驳回的候选为终态并保留审计记录；再次投稿会创建新的不可变候选修订。
- 任意普通用户可以基于已发布内容发起新修订，但不能直接覆盖线上修订。
- 归档只允许对应知识库的审查管理员或系统管理员执行。
- 所有关键动作保留操作者、时间和完整审计记录。

## 4. 创建、修订与审核流程

### 4.1 新建父类

前端展示父类字段和主子条目字段。一次提交原子创建：

- 父类；
- 该父类唯一的主子条目；
- 主子条目的一个不可变修订；
- 用户选择的一个或多个目标知识库。

审核单元类型为 `parent_with_primary`。每个目标知识库只需一名获授权审查管理员通过；全部目标知识库都通过且所需索引全部准备就绪后，父类—主子条目聚合才整体生效。任一内容变更都会产生新修订，并使此前针对旧候选修订的批准失效，所有相关知识库必须重新审核。

### 4.2 新建普通子条目

普通子条目的内容字段可以在尚未选择父类时填写或暂存。正式提交时必须选择一个可用父类，并选择一个或多个允许的目标知识库；目标集合必须是该父类主子条目已发布知识库的子集。

审核单元类型为 `child`。每个目标知识库独立审核、索引和生效；A 库审核失败不阻止 B 库使用其已批准修订。

### 4.3 修改已发布内容

- 不修改已发布行，而是创建不可变新修订。
- 普通子条目可以按目标知识库独立提交新修订，各库的 `active_revision_id` 可以不同。
- 父类与主子条目始终共同修订，并执行全局一致发布规则。
- 修订提交后进入审核；审核通过自动创建异步嵌入/写索引任务。
- 所需索引全部成功后自动发布，无额外“发布”按钮。
- 索引失败时记录失败状态并按退避策略重试；内容未变化时无需重新审核，旧当前修订继续服务。

### 4.4 概念状态机

候选修订主流程：

```text
pending_review → indexing → published
       └──────→ rejected

indexing → index_failed → retry → indexing
```

V1 对同一普通子条目的同一知识库发布关系最多允许一个未结束候选；父类—主子条目聚合全局最多允许一个未结束候选。存在候选时重复提交直接返回冲突，不实现并行候选合并、撤回或自动变基。

归档状态位于 `子条目 × 知识库` 发布关系。归档 A 库不会影响 B 库。关系库状态更新后检索立即不可见，向量清理由异步任务完成。

## 5. 关系数据库设计方向

采用 PostgreSQL、SQLAlchemy 2 和 Alembic。最终表名可在实现阶段统一，但数据模型至少需要表达以下实体与关系：

- `user_account`：账号、角色、启停状态、凭据与审计字段。
- `knowledge_base`：业务知识库、逻辑标识、状态及当前物理 Collection 代。
- `reviewer_knowledge_base`：审查管理员与知识库多对多授权。
- `parent`、`parent_revision`：父类身份与不可变内容修订。
- `parent_lexical_rule`：规范关键词、别名和受控正则等词法规则。
- `child`、`child_revision`：子条目身份、是否为主子条目、不可变内容修订。
- `child_revision_question_variant`：同义问句规范化表，包含稳定 ID 与排序。
- `revision_target` / `review_submission` / `review_decision`：候选修订投放、审核任务和每库决定。
- `child_knowledge_base_publication`：`child_id + knowledge_base_id` 唯一，保存发布状态、`active_revision_id`、归档信息及有用次数缓存。
- `evidence_attachment`、`web_link`：绑定到不可变子条目修订的佐证材料。
- `index_job` / `outbox_job`：持久异步任务、重试、租约/锁和幂等键。
- `search_interaction`：一次用户可感知的向量或快速检索，记录发起用户、目标知识库、无匹配/降级状态及时间。
- `search_event`、`search_result_item`、`helpful_feedback_event`：查询级检索上下文、返回项和逐条“有用”反馈事件；`search_event` 可按顺序归属一个 `search_interaction`。
- `search_annotation_review`：一条检索交互最多一个、不可修改的完成 Review，保存提交用户、实际展示结果数和时间。
- `search_annotation_result_feedback`：Review 内每条实际展示结果的一条标签，保存结果 ID、四种标签之一及仅“其他”可用的说明。
- `knowledge_draft`：仅用于新增普通子条目的创建者私有暂存数据，来源为手动保存或智能生成；它不是不可变修订或审核提交。
- `intelligent_ingestion_batch`：快速上传的异步处理状态、幂等信息、临时输入生命周期和生成结果摘要。
- `audit_event`：管理、投稿、审核、发布、归档等关键行为审计。

原始表设计必须修正的内容：

- 删除父表上的 `collections TEXT`，改为规范化的投放/发布关系。
- 子条目使用独立 `child_id`，不能复用父类 `entry_id` 作为子表主键。
- 内容身份、不可变修订和分库发布状态分离，不能只靠实体表上的单一 `status/version`。
- `question_variants_json` 改为明细表。
- `attachments_json` 改为附件明细表。
- `hit_count` 语义改为 `helpful_count`；反馈事件是事实来源，计数字段只是聚合缓存。

具体 DDL、约束名和索引仍需在实施前完成最终审查。

## 6. 向量与检索索引

### 6.1 Milvus 记录粒度

每条 Milvus 记录是一个向量分片，至少携带：

- 内部向量记录 ID；
- `child_id`；
- `child_revision_id` 或等价不可变版本标识；
- 稳定 `source_item_id`；
- 受控 `field_type`；
- `field_text`；
- 文本稠密向量，维度 1024；
- BM25 使用的稀疏向量字段；
- 必要的校验/追踪元数据。

不再保留：

- 指向父类的模糊 `entry_id`；
- 每行 `weight`；字段权重由应用检索配置管理，可不重写向量直接调整；
- `vl_embedding`；V1 不对知识附件做视觉向量检索。

### 6.2 嵌入来源

V1 只嵌入：

- `question`：一个向量分片；
- 每条 `question_variant`：各自一个向量分片；
- `response_content`：短文本一个分片，长文本按固定 tokenizer、窗口和 overlap 确定性切分，并保存稳定来源信息与内容哈希。

V1 不嵌入：

- `feature_explanation`、`example`；它们只随结果返回；
- `type`、`object`、`purpose`、`customer_type`；它们是结构化元数据；
- 内部 `notes`；
- 附件和网页本体。

同一子条目产生的多个向量候选先按 `max(similarity × field_type_weight)` 聚合，不能作为多个最终结果占位。

### 6.3 模型与混合检索

- 稠密嵌入模型固定为 `Qwen/Qwen3-Embedding-0.6B`，输出 1024 维；`BAAI/bge-m3` 只作为评测基线。
- 使用 Milvus 稠密向量与内置 BM25 稀疏向量混合召回，并配置适合中文的 Jieba 分词分析器。
- 本地重排模型固定为 `Qwen/Qwen3-Reranker-0.6B`。
- 模型升级不在现有物理 Collection 中混写。为知识库创建新物理 Collection 代、全量重建和验证，通过后原子切换关系库映射，再延迟清理旧代。

## 7. 检索输入、排序和输出

### 7.1 查询输入

支持：

- 纯文本问题；
- 文本问题加查询图片；
- 仅查询图片。

查询图片只用于 OCR。OCR 采用固定版本 `PP-OCRv6_medium`，得到清洗文本、关键词、置信度和模型版本。原图只作临时处理并在短 TTL 后清除；日志只保留清洗后的 OCR 信息和图片哈希。

文本问题与 OCR 文本是两个独立查询通道，分别嵌入和召回后融合；存在用户文本时其权重更高，图片-only 查询使用 OCR 通道。OCR 只有在高置信度且命中受控精确词/别名规则时才触发父类关键词保底，并标记 `ocr_keyword_fallback`。

### 7.2 排序管线

确定的顺序为：

1. 每个查询通道执行稠密向量 + BM25 混合召回。
2. 融合用户文本与 OCR 通道候选。
3. 同一 `子条目修订 × 知识库` 的多个分片取最高混合分，候选池默认最多 24 项。
4. 存在混合分不低于 `SEARCH_HIGH_CONFIDENCE_THRESHOLD`（默认 0.7）的候选时，直接返回第一阶段所有混合分大于 0 的召回结果；不调用后续模型。
5. 否则对完整子条目（问题、同义问句、回复）重排；存在重排分不低于 `SEARCH_RERANK_THRESHOLD`（默认 0.5）的候选时只返回这些候选。
6. 重排无合格项或服务不可用时，使用已配置 LLM 对候选逐项进行严格二元相关度判断；LLM 只判定，不生成答案。
7. LLM 未配置、失败或返回无效结构时，按原始混合分不低于 `SEARCH_FALLBACK_THRESHOLD`（默认 0.22）兜底；仅在实际返回该层候选时标记模型降级。LLM 成功且全部判无关时返回无匹配。
8. 所有门槛都使用未加点赞的原始分数。通过门槛后才使用按 `子条目 × 知识库` 统计的 `helpful_count` 添加有上限的对数增益，并按综合相关度、点赞数、稳定原始顺序排序。
9. 注入必须出现的主子条目关键词保底结果。
10. 按全局父类分组；父类组分数取组内子条目最高分，不累加子条目数量。

### 7.3 父类关键词保底

- 查询命中父类主关键词、别名或受控正则时，即使普通子条目没有召回，也保证该父类主子条目出现。
- 匹配质量顺序为：规范关键词精确匹配 > 别名匹配 > 正则匹配；更具体的长词优先。
- 保底注入数量可配置，默认最多 3 个父类。
- 主子条目自然召回时使用正常相关分，不重复插入。
- 同一父类既有正常子条目又触发保底时，正常语义命中排在保底项之前。
- 结果携带可解释的 `match_reason`。

### 7.4 结果形态

父类只展示一次，子结果保留知识库维度，不做跨库去重：

```text
父类 X
  - 子条目 1（知识库 A 当前版本）
  - 子条目 2（知识库 A 当前版本）
  - 子条目 3（知识库 B 当前版本）
```

每个命中返回该子条目当前修订的全部对外字段和佐证附件，但使用明确白名单。内部备注、用户隐私、审核细节、审计信息及索引元数据不得对外返回。

没有候选达到可配置相关性阈值且未触发父类关键词保底时，返回结构化 `no_match` 以及固定“转研发查询”指引，不伪造知识结果，也不能提交逐条“有用”反馈；但该次向量或快速检索仍可完成零结果 Review，`no_match` 作为检索事实保留。

### 7.5 有用反馈

- 用户必须主动选择某个真正有用的结果并提交事件，不能以曝光或普通点击计数。
- 计数维度为 `child_id × knowledge_base_id`。
- 事件至少绑定 `user_id、search_event_id、child_id、knowledge_base_id、child_revision_id`。
- 同一搜索事件中的同一用户、子条目及修订使用幂等约束，API 重试不能重复计数。
- 同一用户在后续不同搜索事件中可以再次反馈同一子条目。
- 反馈事件是事实来源，发布关系上的 `helpful_count` 只是可重算聚合。

### 7.6 检索 Review 与结果级标注反馈

- `helpful_feedback_event` 与结果级标注的语义严格分离：前者表示某一已展示知识条目有帮助，并影响其后续排序加成；后者只记录评价事实，不改变 `helpful_count`、分数、阈值或排序。
- 每次向量检索创建一个 `search_interaction` 并关联一条有序 `search_event`；一次快速检索或编辑后的批量检索创建一个 `quick_search` 交互并按查询顺序关联 1–5 条事件。字段筛选和未提取到查询的快速检索不创建交互，也不展示标注入口。
- 一次检索是一个不可修改的 `search_annotation_review`。用户先在浏览器中逐条处理实际展示的去重结果，完成后原子提交整次 Review；服务端要求请求中的结果 ID 集合与按展示规则重建的集合完全一致。
- 每条结果的标签固定为 `high_score_irrelevant`、`low_score_relevant`、`normal`、`other`。`normal` 是“结果正常”，对应页面的“跳过”，表示高分有关或低分无关，不是未标注。`other` 必须在去除首尾空白后非空且不超过 4000 字；其他三类不接受说明。
- 每个交互最多一个完成 Review，只能由检索发起者通过 CSRF 提交。相同的完整结果标签集合重试返回已记录；不同内容再次提交返回冲突；不提供修改或删除接口。
- 标注请求不得传递查询文本。展示、分析和后台详情只能读取服务端持久化的 `search_event.query_text` 与 `ocr_text`；快速检索保留本次实际执行的全部查询并在结果层复用其去重规则。
- 无匹配交互可完成零结果 Review，`no_match` 保留为检索事实。若未来要区分漏召回与正常无结果，必须增加明确的检索级原因，不能把无结果解释为某条结果标签。

### 7.7 标注数据面板

- 仅系统管理员可以访问汇总、明细和详情。明细以完成 Review 为行，默认每页 20 条，按提交时间倒序。
- 汇总按标注时间、知识库和查询关键词筛选，显示已完成 Review 数、已标注结果数及四种结果标签的完整分布；明细可额外按结果标签筛选，显示至少包含该标签的 Review，该筛选不改变汇总分布。
- 知识库筛选同时匹配明确指定的目标知识库和当时实际返回条目所属的知识库。详情只重建已展示的结果，按查询顺序展示每条结果的标签和说明，并复用快速检索的去重、最佳分数和命中查询规则；不暴露隐藏候选。

## 8. 附件与对象存储

- 附件仅作为回答佐证材料，绑定到不可变子条目修订。
- PostgreSQL 保存对象键、原始文件名、MIME、大小、校验和及修订关系。
- 客户端通过短时签名 URL 访问，Bucket 不公开。
- V1 附件类型白名单为 PNG、JPEG、WebP、PDF、DOCX、XLSX、PPTX、TXT；禁止 SVG、HTML、压缩包、可执行文件、脚本和带宏 Office 文件。
- 单文件最大 20 MB；每个修订最多 10 个附件、附件总量最大 100 MB。三个限制均由后端强制执行，前端限制只用于提前提示。
- 上传时同时校验规范化扩展名、探测 MIME 和文件签名，不能信任客户端声明的 `Content-Type`；对象键由系统生成 UUID，原文件名只作为经过清洗的展示元数据。
- 新文件先存入业务附件的非公开隔离区，由本地 ClamAV 服务异步扫描。只有状态为 `clean` 的附件才能随修订提交审核；感染、扫描错误或超时均阻止提交。
- 前端只允许内嵌预览通过验证的图片；PDF、Office 和文本附件使用短时签名 URL 并通过响应头强制下载。
- Milvus 与业务附件共用同一个 MinIO 服务，但使用不同 Bucket、不同凭据和最小权限策略。
- 业务服务只能操作附件 Bucket；备份、清理和生命周期策略与 Milvus Bucket 分开。

## 9. 异步任务与一致性

- PostgreSQL 持久任务/Outbox 表承担审核后嵌入、写索引、重试、归档清理等任务，不引入 Redis/RabbitMQ。
- Worker 使用 `FOR UPDATE SKIP LOCKED` 竞争任务，并实现租约、指数退避、最大重试和业务幂等键。
- 同一不可变修订的嵌入结果只计算一次，再写入已经批准该修订的各目标 Collection。
- 发布事务必须验证审核版本、索引版本和当前候选仍一致，防止过期任务激活旧内容。
- 检索从 Milvus 得到候选后，必须回查 PostgreSQL 的发布状态和 `active_revision_id`；已归档或已切版候选立即过滤。

## 10. 认证与账号

- 不开放自助注册；系统管理员创建、禁用账号和重置凭据。
- 密码使用 Argon2id 哈希保存；参数根据部署机器基准测试校准，并且不得低于当前 OWASP 推荐下限。
- 首次启动仅在账号表为空时，从 Docker Secret 创建一个系统管理员，并将其标记为首次登录必须修改密码；初始化完成后不得因环境变量或 Secret 变化重复创建或覆盖管理员。
- 系统管理员修改自己的密码必须输入当前密码并自定义新密码；账号管理的临时密码重置不适用于系统管理员。
- 系统管理员重置其他账号时，生成密码学安全的随机一次性临时密码，仅展示一次，并要求用户下次登录立即修改。
- 不提供公开的“忘记密码”或邮件找回入口；遗忘密码统一由系统管理员核验身份后重置。
- 使用单个无状态 JWT，存放于 `HttpOnly` Cookie，不引入服务端会话或 Refresh Token。
- Token 固定有效期约 8 小时，到期重新登录。
- 每个请求均回查账号是否启用及当前角色/授权，禁用和权限变更应立即生效。
- JWT 携带账号当前 `token_version`；改密、管理员重置密码或禁用账号时递增数据库中的版本，使全部旧 JWT 在下一次请求时立即失效。
- 所有变更型请求具备 CSRF 防护。

## 11. 服务端与前端技术栈

### 后端

- Python 3.12；默认使用项目虚拟环境。
- FastAPI、Pydantic、SQLAlchemy 2、Alembic。
- API 与异步 Worker 为独立进程/容器，但共享领域代码和基础设施适配器。

### 前端

- React + TypeScript + Vite + Ant Design。
- 至少包含：登录/账号管理、知识库管理、审查管理员分配、父类+主子条目/普通子条目表单、普通子条目草稿与快速上传、审核队列、文本/图片检索、会话快速检索、按父类分组结果、逐条有用反馈、结果级检索 Review 标注和系统管理员数据面板。
- Nginx 容器托管静态资源并反向代理 API。

## 12. 部署拓扑

最终 `docker-compose.yaml` 至少覆盖以下职责：

- `nginx`；
- `web` 构建产物或构建阶段；
- `api`；
- `worker`；
- `postgres`；
- `milvus-standalone` 及其必要依赖；
- 共享但权限隔离的 `minio`；
- 本地 `clamav` 附件扫描服务；
- 生产环境的本地嵌入、重排和 OCR 模型服务。

环境差异：

- 生产服务器有 NVIDIA GPU，模型服务使用 CUDA 容器，整个系统保持离线/本地部署。
- macOS 测试环境没有 CUDA；嵌入和重排模型允许在宿主机使用 MPS 启动，OCR 在宿主机使用 CPU/ONNX，其他服务由 Compose 运行。
- API/Worker 只依赖稳定的 HTTP 模型服务协议，通过环境变量切换宿主机测试端点与生产容器端点。
- LLM 会话处理使用可配置的 OpenAI 协议兼容接口，服务地址、密钥、模型名称与超时由部署环境提供。
- 所有镜像和模型版本在交付时固定，不使用漂移的 `latest`。
