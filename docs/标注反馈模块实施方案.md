# 检索 Review 与结果级标注反馈

## Summary

- 一次检索仍是一个不可修改的 Review 提交单元；标签的单位改为该 Review 中每一条实际展示的去重结果。
- 每条结果可标为 `high_score_irrelevant`（高分无关）、`low_score_relevant`（低分有关）、`normal`（结果正常）或 `other`（其他）。
- 页面中的“跳过”会写入 `normal`，表示该结果不存在需要报告的排序问题：高分有关或低分无关；它不是“未处理”。
- 用户在本地逐条完成结果标签，最后原子提交整次 Review。原有逐条“有用”反馈及排序加成保持独立。
- 覆盖向量检索、OCR 检索和整次快速检索；字段筛选不提供标注。无匹配可以完成零结果 Review；快速检索未提取出查询时不提供标注。
- 首版仅记录和分析，不自动调整分数、阈值或线上排序，也不保存被过滤的隐藏候选。

## 数据与检索模块

- `SearchInteraction` 是一次用户可感知检索的边界：
  - 类型为 `vector` 或 `quick_search`。
  - 记录用户、目标知识库、无匹配状态、降级状态及原因、创建时间。
  - `SearchEvent` 持有可空的 `search_interaction_id` 与查询顺序；单次向量检索关联一条事件，快速检索按顺序关联多条查询事件。
- 新增 `SearchAnnotationReview`：
  - 每个 `search_interaction_id` 最多一个完成的 Review，保存提交用户、展示结果数和提交时间。
  - Review 只能由交互发起者提交；相同内容重试返回 `already_recorded=true`，不同内容再次提交返回 `409`，不提供修改或删除接口。
- 新增 `SearchAnnotationResultFeedback`：
  - 每条记录关联一个 Review 与一个 `search_result_item_id`，同一 Review 内同一结果最多一条标签。
  - 标签固定为 `high_score_irrelevant`、`low_score_relevant`、`normal`、`other`。
  - `other` 必须提供去除首尾空白后非空、最长 4000 字的说明；其他三类不接受说明。
  - 提交时的结果 ID 集合必须与服务端按实际展示规则重建的去重结果集合完全一致，避免漏标、伪造或标注隐藏候选；无匹配时只接受空列表。
- 旧的 `search_annotation_feedback` 迁移表保留为历史审计数据，不被新读写路径使用。旧的交互级标签不能诚实地推断为任意结果级标签。
- 查询语句始终从服务端已持久化的 `SearchEvent.query_text/ocr_text` 读取，标注请求不接收查询文本。快速检索保存并关联本次全部查询。
- 多查询执行、结果去重、最佳分数选择及命中查询展示规则集中于 `app.services.search_batch`，供会话快速检索、编辑查询后的重新检索、Review 校验和后台详情复用。

## HTTP 接口与前端

- 检索接口：
  - `POST /api/v1/search` 的向量响应包含 `search_interaction_id`；字段筛选返回 `null`。
  - `POST /api/v1/search/conversation-assist` 与 `POST /api/v1/search/query-batch` 返回整次快速检索的 `search_interaction_id`；无提取查询时返回 `null`。
- 标注接口：
  - `POST /api/v1/search/interactions/{interaction_id}/annotation-feedback` 接收 `result_feedbacks` 数组；每项包含 `search_result_item_id`、`feedback_type` 和仅 `other` 可用的 `other_note`。
  - 仅检索发起者可提交并要求 CSRF；不存在、非本人或不可标注的交互不泄露详情。
- 检索页在整个结果区域增加“本次检索标注”入口，而不是把 Review 变成每条结果的独立提交：
  - 点击“开始逐条标注”后依次展示结果，提供“高分无关”“低分有关”“跳过（结果正常）”和“其他”。前三项选择后进入下一条；“其他”需要填写说明后继续。
  - 可返回修改本地草稿；全部结果处理完后，点击“完成并提交”一次性提交整个 Review。
  - 无匹配状态可完成零结果 Review；字段筛选和“未发现待查询问题”不展示入口。
  - 成功后显示已标注状态；原有每条结果的“有用”按钮保持不变。
- 系统管理员的“数据面板 / 标注反馈”：
  - 汇总展示已完成 Review 数、已标注结果数及四种结果标签数量。
  - 明细按 Review 展示用户、检索类型、查询语句、目标知识库、各标签数量、检索时间、提交时间和展示结果数；默认每页 20 条。
  - 支持标注时间、知识库、查询关键词与结果标签筛选。标签筛选显示至少含有该标签的 Review，汇总仍保留当前时间/知识库/关键词范围内的完整分布。
  - 展开详情按查询顺序展示当时实际返回的知识条目及其结果标签、其他说明、父类/问题、知识库、排名、分数、命中阶段、命中字段和命中查询；不展示隐藏候选。

## Test Plan

- 后端验证单查询和快速检索正确创建交互、关联有序查询，并覆盖文本、OCR、混合查询、无匹配及无查询场景。
- 验证四种结果标签、其他说明、所有权、CSRF、完整覆盖校验、不可修改、幂等重试和并发唯一约束；确认 Review 不会改变 `helpful_count` 或排序。
- 验证快速检索的展示去重规则与 Review 校验、管理员详情重建一致。
- 验证管理员 Review 汇总、结果标签汇总、组合筛选、分页、详情重建和角色权限，覆盖快速检索多查询及零结果 Review。
- 前端验证逐条向导、“跳过 = 结果正常”、其他说明、最终原子提交、成功锁定、原有“有用”反馈不回归，以及数据面板的筛选和展开详情。
- 使用项目 Python 3.12 虚拟环境执行后端测试与 Ruff，并执行前端 Vitest 和生产构建；验证 Alembic 从 `0011_search_annotation` 升级到 `0012_result_annotations`。

## Assumptions

- “高分/低分”由用户主观判断，后端不依据当前阈值拒绝或自动改写标签。
- `normal` 是显式的正常结果标签，不是未标注状态；每个展示结果必须拥有四种标签之一。
- 无匹配 Review 没有结果级标签，`search_interaction.no_match` 仍保留该检索事实。若后续需要区分“正常无结果”和“漏召回”，应新增明确的检索级原因字段，而不是滥用结果标签。
- 快速检索的一次 Review 代表整次多查询合并结果，但每条合并后实际展示的结果各有一个标签。
- 首版不回填历史检索、不导出 CSV、不增加趋势图，也不采集未展示候选。
