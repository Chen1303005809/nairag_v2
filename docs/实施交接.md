# 实施交接

> 更新时间：2026-08-21

本文件供下一位实施者或后续 task 直接续作；它记录已落地的契约和明确留待下一模块的职责，不替代实施基线。

## 当前可用模块

1. 账号与认证：首次系统管理员初始化、Cookie JWT、CSRF、强制改密、账号管理和审计。
2. 知识库与审查授权：知识库启停、逻辑标识与物理 Collection 代映射、审查管理员分配。
3. 父类、子条目与审核提交：不可变内容修订、父类—主子条目原子投稿、普通子条目投稿、目标知识库投放和“我的投稿”界面。
4. 审查工作台与发布状态：按知识库授权过滤审核队列、不可变审核决定、父类聚合全局发布、普通子条目分库发布和归档。
5. 异步索引与检索基础：持久化索引任务、租约/重试、发布事实回查、文本检索、父类关键词保底和有用反馈。
6. 稠密/BM25 检索适配：Qwen HTTP embedding/reranker、PyMilvus `MilvusClient` hybrid search 和离线 artifact 混合召回。
7. 图片 OCR、子条目附件与相关网页链接：材料绑定不可变修订、经审核后随检索结果展示，并使用私有对象存储。
8. 快速上传与快速检索：普通子条目私有草稿、异步会话知识提取、同步会话查询提取与跨查询去重结果展示。

系统管理员密码修改使用 `/api/v1/auth/change-password` 的自定义新密码流程；账号管理临时重置接口不适用于系统管理员。

数据库迁移当前头部为 `0008_fast_upload_drafts`。

## 本模块的领域契约

- `parent` 只保存全局身份；显示名称、规范关键词和词法规则只存在于不可变的 `parent_revision`。
- 每个公开创建路径会原子创建一个父类、唯一主子条目、两份首修订和一条 `parent_with_primary` 审核提交。数据库用部分唯一索引阻止一个父类拥有多个主子条目；不存在独立创建父类或迁移主子条目的接口。
- 普通子条目必须先通过 `parent_with_primary` 的已发布状态，并且目标知识库必须是主子条目已发布知识库的子集。
- `review_submission` 是候选审核单元；`review_submission_target` 表示每个目标知识库的独立审核状态。父类聚合在数据库与服务层均限制为最多一个未结束候选。
- `child_knowledge_base_publication` 是后续发布、归档和有用反馈的持久槽位。新投稿会写入 `pending_submission_id`，因此同一普通子条目在同一知识库不能同时存在两个未结束候选。
- 所有内容修改都新建 `parent_revision` 或 `child_revision`，现有修订没有更新接口。
- `knowledge_draft` 是创建者私有、可变的普通子条目暂存数据，不是 `child`、`child_revision` 或 `review_submission`；正式提交成功后在同一事务中删除草稿。
- `intelligent_ingestion_batch.normalized_messages` 只保存快速上传的短期输入。完成、失败或超过 24 小时后必须物理清空；草稿仅保留来源哈希、提取时间和模型版本等元数据。
- 智能生成草稿以“批次 + 候选内容 SHA-256”去重，保证租约恢复或重试不会产生重复草稿。

- `GET /api/v1/knowledge-content/submissions/mine`
- `GET /api/v1/knowledge-content/review-queue`
- `POST /api/v1/knowledge-content/review-submissions/{submission_id}/targets/{knowledge_base_id}/decision`
- `GET /api/v1/knowledge-content/children/{child_id}/publications/{knowledge_base_id}`

前端的 `web/src/pages/ContentSubmissionPage.tsx` 提供快速上传、手动暂存普通子条目草稿、我的草稿、父类—主子条目、普通子条目以及“我的投稿”界面。没有可选父类时仍可编辑和暂存普通子条目草稿，提交前才要求父类和合法目标知识库。
审查管理员和系统管理员可在 `web/src/pages/ReviewWorkbenchPage.tsx` 查看授权范围内的待审核目标并记录通过/驳回决定。
普通用户、审查管理员和系统管理员可在 `web/src/pages/SearchPage.tsx` 进行文本、OCR 图片和快速会话检索，并提交有用反馈。

审核决定接口只推进目标到 `approved` 或 `rejected`；索引完成后的发布由 `app.services.knowledge_content.publish_approved_target` 提供事务性入口。普通子条目只切换当前目标库的发布关系，父类—主子条目则要求全部目标准备完毕后一次性切换。
审核通过会在同一事务中创建幂等 `index_job`。`app.services.index_jobs` 提供任务领取、租约、重试和完成入口；`LocalArtifactIndexBackend` 生成确定性开发向量、BM25 词项和原子写入的 JSON 分片，worker 成功后才推进 PostgreSQL 发布状态。

索引后端由 `INDEX_BACKEND_MODE` 选择：`local_artifact` 用于离线开发和契约测试；`milvus` 使用 `Qwen/Qwen3-Embedding-0.6B` 的 OpenAI-compatible HTTP embedding 服务，并通过 Milvus REST v2 upsert 写入当前物理 Collection。检索默认从 artifact 执行稠密向量 + BM25 混合召回，可配置 `Qwen/Qwen3-Reranker-0.6B` HTTP 服务；Milvus 模式使用 PyMilvus `MilvusClient`，逐条查询构造 dense/BM25 `AnnSearchRequest`，每次只使用一个 `WeightedRanker`，最终仍由 PostgreSQL 回查当前发布版本。

独立 worker 入口为 `backend/worker.py`，默认循环运行并响应 `SIGINT`/`SIGTERM` 优雅停机；`python worker.py --once` 可用于一次性排查任务。它在每轮中分别尝试一个索引任务和一个智能生成批次，避免持续索引负载饿死快速上传；即使 LLM 暂未配置，也会继续清理超过 24 小时的原始聊天。配置项为 `INDEX_ARTIFACT_DIR`、`WORKER_ID`、`WORKER_POLL_INTERVAL_SECONDS`、`WORKER_LEASE_SECONDS`、`OPENAI_BASE_URL`、`OPENAI_KEY`、`OPENAI_MODEL` 及会话输入上限。Compose 中的 `worker` 服务与 API 共用 PostgreSQL Secret，并将产物写入项目目录下、已被 Git 忽略的 `volumes/index_artifacts`。

当前已达到的基础文本业务闭环是：投稿 → 按知识库审核 → PostgreSQL 持久化索引任务 → worker 生成索引并自动发布 → API 从共享 artifact/Milvus 候选回查当前发布修订 → 返回分组结果 → 用户提交幂等有用反馈。Compose 中 API 以只读方式挂载 `volumes/index_artifacts`，worker 以读写方式挂载，保证检索进程能读取 worker 的最新产物。

快速上传与快速检索的实施基线见 [快速上传与快速检索实施基线.md](快速上传与快速检索实施基线.md)。网页端将企业微信转发卡片解析为标准消息：支持 `8-17 11:28` 时间格式，说话人名称中包含“融航”即我方；卡片的 `[图片]` 会按出现顺序调用 OCR 后替换为文字。转发卡片未携带原图时，轻量富文本会话框可为每个图片占位符单独粘贴或选择图片，删除一个占位符只移除它自身的图片。网页与后端共同校验会话上限。快速上传必须识别双方发言，创建可离开页面的异步批次；完成后仅创建当前用户可见的普通子条目草稿。快速检索不保存原会话，LLM 只提取最多五条去身份化的待查询语句，服务端逐条检索、按 `子条目修订 × 知识库` 去重，并在统一结果区标注命中的查询。

## 本轮已完成的附件能力与后续模块

已完成图片 OCR、子条目附件与相关网页链接：附件记录绑定到不可变 `child_revision`，保存系统生成对象键、MIME、大小和 SHA-256；上传时校验扩展名、声明 MIME、文件签名及 Office 容器，并拒绝带宏 Office 文件。开发/测试使用本地私有目录，生产 Compose 使用与 Milvus 共用的 MinIO 服务中的独立 Bucket、独立凭据和最小权限策略。附件及链接会随投稿进入审核，并在审核、管理和检索结果中展示。

后续应承接而不是重建当前模型：

1. 为 Milvus Collection 创建/验证固定 schema、BM25 Function 和 generation 切换流程；继续复用 `IndexFragment`、稳定 `source_item_id` 和任务幂等键。
2. 接入 ClamAV 隔离/扫描状态和相应的持久化任务，使只有扫描通过的附件可随修订提交；保持 PostgreSQL 的发布状态与 `active_revision_id` 为唯一事实来源。
3. 完成模型服务、Milvus、MinIO、ClamAV 的 Compose/健康检查和离线部署验收。
