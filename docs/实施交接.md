## 当前可用模块

1. 账号与认证：首次系统管理员初始化、Cookie JWT、CSRF、强制改密、账号管理和审计。
2. 知识库与审查授权：知识库启停、逻辑标识与物理 Collection 代映射、审查管理员分配。
3. 父类、子条目与审核提交：不可变内容修订、父类—主子条目原子投稿、普通子条目投稿、目标知识库投放和“我的投稿”界面。
4. 审查工作台与发布状态：按知识库授权过滤审核队列、不可变审核决定、父类聚合全局发布、普通子条目分库发布和归档。
5. 异步索引与检索基础：持久化索引任务、租约/重试、发布事实回查、文本检索、父类关键词保底和有用反馈。
6. 稠密/BM25 检索适配：Qwen HTTP embedding/reranker、Milvus REST upsert/hybrid-search 网关和离线 artifact 混合召回。

数据库迁移当前头部为 `0005_index_jobs_and_search_events`。

## 本模块的领域契约

- `parent` 只保存全局身份；显示名称、规范关键词和词法规则只存在于不可变的 `parent_revision`。
- 每个公开创建路径会原子创建一个父类、唯一主子条目、两份首修订和一条 `parent_with_primary` 审核提交。数据库用部分唯一索引阻止一个父类拥有多个主子条目；不存在独立创建父类或迁移主子条目的接口。
- 普通子条目必须先通过 `parent_with_primary` 的已发布状态，并且目标知识库必须是主子条目已发布知识库的子集。
- `review_submission` 是候选审核单元；`review_submission_target` 表示每个目标知识库的独立审核状态。父类聚合在数据库与服务层均限制为最多一个未结束候选。
- `child_knowledge_base_publication` 是后续发布、归档和有用反馈的持久槽位。新投稿会写入 `pending_submission_id`，因此同一普通子条目在同一知识库不能同时存在两个未结束候选。
- 所有内容修改都新建 `parent_revision` 或 `child_revision`，现有修订没有更新接口。

## 已提供的 API 与界面

后端路由位于 `backend/app/api/routes/knowledge_content.py`：

- `POST /api/v1/knowledge-content/parent-submissions`
- `POST /api/v1/knowledge-content/child-submissions`
- `POST /api/v1/knowledge-content/parents/{parent_id}/revisions`
- `POST /api/v1/knowledge-content/children/{child_id}/revisions`
- `GET /api/v1/knowledge-content/parents/available`
- `GET /api/v1/knowledge-content/submissions/mine`
- `GET /api/v1/knowledge-content/review-queue`
- `POST /api/v1/knowledge-content/review-submissions/{submission_id}/targets/{knowledge_base_id}/decision`
- `GET /api/v1/knowledge-content/children/{child_id}/publications/{knowledge_base_id}`
- `POST /api/v1/knowledge-content/children/{child_id}/publications/{knowledge_base_id}/archive`

前端的 `web/src/pages/ContentSubmissionPage.tsx` 已提供新建父类—主子条目、普通子条目以及“我的投稿”三个界面。普通子条目在当前没有已发布父类时会明确显示不可选状态。
审查管理员和系统管理员可在 `web/src/pages/ReviewWorkbenchPage.tsx` 查看授权范围内的待审核目标并记录通过/驳回决定。
普通用户、审查管理员和系统管理员可在 `web/src/pages/SearchPage.tsx` 进行文本检索并提交有用反馈。

审核决定接口只推进目标到 `approved` 或 `rejected`；索引完成后的发布由 `app.services.knowledge_content.publish_approved_target` 提供事务性入口。普通子条目只切换当前目标库的发布关系，父类—主子条目则要求全部目标准备完毕后一次性切换。
审核通过会在同一事务中创建幂等 `index_job`。`app.services.index_jobs` 提供任务领取、租约、重试和完成入口；`LocalArtifactIndexBackend` 生成确定性开发向量、BM25 词项和原子写入的 JSON 分片，worker 成功后才推进 PostgreSQL 发布状态。

索引后端由 `INDEX_BACKEND_MODE` 选择：`local_artifact` 用于离线开发和契约测试；`milvus` 使用 `Qwen/Qwen3-Embedding-0.6B` 的 OpenAI-compatible HTTP embedding 服务，并通过 Milvus REST v2 upsert 写入当前物理 Collection。检索默认从 artifact 执行稠密向量 + BM25 混合召回，可配置 `Qwen/Qwen3-Reranker-0.6B` HTTP 服务；Milvus 模式通过 hybrid-search 网关返回候选，最终仍由 PostgreSQL 回查当前发布版本。

独立 worker 入口为 `backend/worker.py`，默认循环运行并响应 `SIGINT`/`SIGTERM` 优雅停机；`python worker.py --once` 可用于一次性排查任务。配置项为 `INDEX_ARTIFACT_DIR`、`WORKER_ID`、`WORKER_POLL_INTERVAL_SECONDS` 和 `WORKER_LEASE_SECONDS`。Compose 中的 `worker` 服务与 API 共用 PostgreSQL Secret，并将产物写入独立 `index_artifacts` volume。

## 下一模块必须实现

下一模块是“附件/OCR 与生产 Collection 生命周期”，应承接而不是重建当前模型：

1. 为 Milvus Collection 创建/验证固定 schema、BM25 Function 和 generation 切换流程；继续复用 `IndexFragment`、稳定 `source_item_id` 和任务幂等键。
2. 接入图片 OCR、附件白名单/对象存储和检索结果佐证附件；继续保持 PostgreSQL 的发布状态与 `active_revision_id` 为唯一事实来源。
3. 完成模型服务、Milvus、MinIO、ClamAV 的 Compose/健康检查和离线部署验收。
